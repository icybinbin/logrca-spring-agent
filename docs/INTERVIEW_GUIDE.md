# 智能日志 RCA Agent：面试追问指南

> 版本说明：下文保留离线版本和早期 OpenAI 适配器的追问。当前主要真实模型入口是 DeepSeek，已记录请求次数、Token 和工具 Trace，并提供文件上传与证据核对；具体实现、预算和失败处理以 [README](../README.md) 为准。离线成绩不能作为 DeepSeek 成绩，协议模拟测试也不能作为真实模型效果验证。

> 这份文档不是背诵一套“万能话术”，而是帮助你把回答绑定到真实源码。面试时最稳妥的顺序是：**先讲结论，再指向本项目中的实现，最后主动说清取舍和限制**。凡是你还没有亲自运行、读懂、解释清楚的内容，不要先写进简历。

## 一页事实卡：先把项目边界说准确

这个 Demo 解决的是：把多格式日志统一成事件，在异常门控后，用有界工具检索日志，由根因假设 Agent 形成候选；在多 Agent 模式中，再由独立证据审核 Agent 核验引用、剔除级联症状，最后生成包含异常判断、疑似根因、证据链、排查项、处置建议和限制的结构化报告。

当前真正实现的内容：

- 默认路径完全离线，可复现，不需要 API Key；决策策略是显式规则，不是假装成大模型。
- 支持 6 个透明的 Spring 风格合成场景：1 个正常场景和 5 类异常场景。
- 支持读取 Loghub 仓库中的 `*_structured.csv`，做统一字段映射、模板压缩统计、事故聚合与 16 数据集接入审计。
- 增加 120-case 标签侧车评测集：8 类已知故障、normal、OOD，含缺证据、干扰、重复、乱序和 trace 破坏；精确 root-evidence 文案/template 不跨 split。
- 支持单 Agent 与多 Agent 对照；多 Agent 增加 Evidence Auditor，专门核验证据。
- 每个工具调用和观察都可以写入 JSONL Trace，最终引用还会经过代码级 `line_id` 校验。
- 提供可选的 OpenAI Agents SDK 适配器，但它与离线主路径隔离；没有安装 SDK、配置 Key 并实际跑通之前，不能说“线上已接入大模型”。
- 当前明确不使用 RAG、向量库或知识图谱；语义签名和按 code 查 Runbook 是普通本地代码。

当前合成集回归结果（以仓库现有 `outputs/benchmark.json` 为准）：单 Agent 和多 Agent 在 6 个封闭场景上的异常 F1、根因准确率均为 1.0；证据精确率从单 Agent 的 0.5882 提升到多 Agent 的 1.0，平均工具调用从 3.333 增至 5.0。**这只是同一故障目录生成和识别的功能回归，不是生产泛化能力证明。**

P0 test 结果（以 `outputs_p0/result.json` 的 manifest 为准）：40 cases 上 Detection F1 为 1.0；无条件 RCA Top-1 为 0.8125，direct 证据仍可见的 26 cases 为 1.0，6 个删 direct 案例全部安全弃权，4 个 OOD 全部弃权；Multi 将 Evidence micro Precision 从 0.4103 提升到 0.9275，工具调用从 3.6 增至 5.4。语料和规则仍由同一项目开发，不能把它称为独立生产泛化结果。

建议先阅读以下源码：

1. `logrca/models.py`：Agent 之间传递的数据契约。
2. `logrca/runtime.py`：最小 Agent 循环与 Trace。
3. `logrca/store.py`：提供给 Agent 的有界工具。
4. `logrca/agents.py`：单/多 Agent 策略与管理器。
5. `logrca/blind_data.py`、`logrca/benchmarking.py`、`logrca/p0_runner.py`：标签侧车、反事实与评测。
6. `logrca/pipeline.py`：真实本地文件的完整链路。
7. `logrca/openai_adapter.py`、`logrca/live_benchmark.py`：可选真实模型路径与重复评测。

## 高频追问 1：你做的到底是 Agent，还是普通规则工作流？

**结论：** 默认离线实现是“具备 Agent 运行时形态的确定性策略”，不是 LLM Agent；整个系统则是确定性数据管道与 Agent 推理层结合的混合架构。

**本项目做法：** `AgentRuntime` 执行 `decide → tool call → observation → next decide → final` 循环，策略会根据已经看到的观察决定下一步工具，而不是提前写死一条函数调用链；`Policy` 协议可由离线规则或真实模型适配器实现。

**取舍与限制：** 规则策略便于离线运行、调试和回归，但只能覆盖已登记模板，泛化能力有限。面试时应直接说“默认策略不是 LLM”，再说明这样设计是为了先把工具、状态、编排、评测这些稳定部分做实。

## 高频追问 2：一个 Agent 由哪些部分组成？

**结论：** 工程上的 Agent 至少包括目标与指令、决策策略、状态、工具、运行循环、终止条件、输出契约、护栏以及可观测性；模型只是决策策略的一种实现。

**本项目做法：** 指令在 `agents.py`；策略是 `OfflineHypothesisPolicy` 等；状态是 `AgentState`；工具在 `IncidentStore` 和 `ToolRegistry`；循环在 `AgentRuntime`；`max_steps` 是终止护栏；Pydantic 模型约束输出；`TraceRecorder` 记录轨迹。

**取舍与限制：** Demo 没有长期记忆、用户画像和自主写操作，因为日志 RCA 不需要这些能力。不要把“Agent = Prompt + LLM”当答案，面试官更关心状态如何流转、工具如何授权、输出如何验证。

## 高频追问 3：Agent 和工作流的边界是什么？

**结论：** 能确定的步骤应由工作流控制，只有需要基于观察动态选择下一步时才交给 Agent；两者不是二选一。

**本项目做法：** 日志解析、字段归一、异常门控、事故聚合和最终引用校验都是确定性代码；根因候选检索与证据审核采用 Agent 循环。Manager 固定掌握“门控—诊断—审核—组装报告”的外层流程。

**取舍与限制：** 这种设计减少不稳定性和 Token 消耗，但自主性低于完全开放式 Agent。生产 RCA 更需要可控和可审计，因此刻意限制自主性是设计选择，不是能力缺失。

## 高频追问 4：为什么异常检测和根因定位要分开？

**结论：** 异常检测回答“是否值得进一步分析”，RCA 回答“最可能是什么原因、证据是什么”，目标和评价指标不同，应该解耦。

**本项目做法：** `AnomalyDetector` 先根据错误等级、告警等级、高风险模板和跨服务情况形成分数；未过阈值就直接返回，不启动诊断 Agent。只有异常事故才进入假设和审核流程。

**取舍与限制：** 当前门控是可解释启发式，不是训练出来的异常模型；阈值在真实环境中要用历史告警和误报成本校准。优势是正常流量不会消耗 LLM Token。

## 高频追问 5：为什么先结构化日志？是不是转成 JSON 就能减少 Token？

**结论：** 结构化的主要价值是统一查询和建立稳定字段，不是“JSON 天然更省 Token”；真正的压缩来自模板字典、事件 ID 序列和按需检索。

**本项目做法：** `LogEvent` 统一 `timestamp/service/level/message/template_id/trace_id` 等字段；`compression_stats` 比较原文、完整事件 JSON、以及“模板字典 + 模板 ID 序列”。Agent 首先检索模板与摘要，只有候选证据才取具体日志。

**取舍与限制：** 完整 JSON 往往比原始文本更长，所以不能宣称“转 JSON 就大幅压缩”。模板化可能丢失参数值，而参数有时正是根因线索，因此证据阶段仍要回取原始行。

## 高频追问 6：不同服务、不同格式的日志怎么统一？

**结论：** 先定义与来源无关的事件契约，再为不同数据源编写 Adapter；不要让 Agent 直接理解所有原始格式。

**本项目做法：** `load_loghub_csv` 从 Loghub 结构化 CSV 中选取 `Content/Message`、`Component/Process/Node`、`Level`、`EventId/EventTemplate` 等候选字段，并构造统一 `LogEvent`。`spring_parser.py` 另实现一个有明确格式契约的 Logback 文本 Adapter，会把 Java stack trace 续行并入首行事件。时间解析失败时保留稳定源顺序。

**取舍与限制：** Spring parser 只承诺支持 README 展示的 demo layout；真实 Spring 日志还需要按企业 Logback Pattern、JSON Layout、容器元数据和租户规范分别校验，不能说已经兼容所有日志格式。

## 高频追问 7：几万甚至几百万行日志如何控制上下文？

**结论：** 不把全量日志放进模型，而是先分区、聚合、门控、检索，再逐步扩大证据范围；Token 优化首先是数据系统问题。

**本项目做法：** 工具默认只返回 20～30 条，单次硬上限 100 条；先查事故摘要，再查 ERROR/WARN，随后只对候选 `line_id` 拉时间线。Incident 本身也有 `max_events` 边界。

**取舍与限制：** 有界检索可能漏掉低等级但关键的 INFO 日志。生产中需要倒排索引、模板索引、Trace 索引、时间窗口回扩和召回率评测，而不是简单提高上下文长度。

## 高频追问 8：多服务日志是怎么关联成一个 Incident 的？

**结论：** 优先使用明确的相关 ID，缺失时才退化为时间窗口；时间接近只代表相关候选，不等于因果。

**本项目做法：** `build_incidents` 先按 trace/request/block ID 精确分组，超大组再切块；没有 ID 的事件按时间窗口和最大事件数聚合，并在 metadata 中记录策略。

**取舍与限制：** 时间窗口会混入并发请求，也可能拆散长事务。生产中应结合 trace_id、span_id、主机、Pod、服务依赖、发布批次和告警实体做多信号关联。

## 高频追问 9：为什么要区分直接证据、支持证据和症状？

**结论：** RCA 的难点不是找到报错行，而是避免把传播链末端的高频错误当成起点；证据需要按因果强度分层。

**本项目做法：** `EvidenceRef.kind` 区分 `direct/support/symptom/contradiction`。例如数据库连接获取超时是直接证据，SQL 连接失败是支持证据，网关 503 和客户端重试只是症状。

**取舍与限制：** 当前分类来自故障目录规则和时间顺序，是可解释启发式，不是严格因果推断。真实系统还需指标、Trace、拓扑与变更记录交叉验证。

## 高频追问 10：根因候选是怎么生成的？

**结论：** 先通过有界工具收集事故摘要、异常行和时间线，再把直接故障模板映射成候选；候选必须携带可定位证据 ID。

**本项目做法：** `OfflineHypothesisPolicy` 依次观察摘要、异常检索、时间线和 Runbook；`diagnostic_signatures.py::CAUSE_SIGNATURES` 定义 9 类故障的直接/支持语义模式，`store.py::RUNBOOKS` 独立维护建议，最终输出 `HypothesisBundle`。

**取舍与限制：** 这是封闭集合分类，遇到未知模板会返回 `unknown`，不会强行给确定结论。若接入 LLM，可提高语言和未知模式理解能力，但必须保留证据约束。

## 高频追问 11：为什么需要 Evidence Auditor？

**结论：** 生成候选和质疑候选是目标相反的任务，独立审核能降低确认偏误，并把“看起来相关”与“能支撑根因”分开。

**本项目做法：** 多 Agent 模式把主假设交给 `OfflineEvidenceAuditPolicy`；它重新读取引用事件、复核时间线，只接受故障目录中的直接/支持模板，并剔除网关错误、重试、熔断等症状。

**取舍与限制：** 审核增加了工具调用和延迟；若审核 Agent 与生成 Agent 使用完全相同的数据和偏见，收益有限。当前提升只在合成集上得到验证，不能推广为“多 Agent 一定更准确”。

## 高频追问 12：为什么不是所有任务都用多 Agent？

**结论：** 只有当职责可清晰分离、错误代价较高且额外验证有价值时，多 Agent 才值得；否则单 Agent 更简单、更便宜。

**本项目做法：** 单 Agent 直接使用假设专家的证据，多 Agent 额外调用审核员。正常事件两种模式都不调用诊断 Agent；只有异常事件才承担额外成本。

**取舍与限制：** 在现有合成集，多 Agent 平均工具调用从 3.333 增加到 5.0。面试中应表达“用评测决定是否拆 Agent”，而不是为了简历亮点机械拆分。

## 高频追问 13：你采用哪种多 Agent 编排方式？

**结论：** 使用 Manager-as-tools：Manager 持有最终控制权，把专家当成有界工具调用，而不是把整个会话控制权永久转交。

**本项目做法：** 离线路径由 `IncidentManager` 调用 Hypothesis Agent，再按模式调用 Evidence Auditor，最后统一组装 `DiagnosisReport`。SDK 适配器也由 Python Manager 顺序运行两个真实 Agent，并强制将最终证据限制为“候选证据 ∩ Auditor.accepted ∩ 当前 Incident 有效 ID”。

**取舍与限制：** Manager 模式便于统一输出、审计和权限控制，但 Manager 可能成为瓶颈。若以后需要长时间、强自治的并行调查，可考虑 handoff 或事件驱动编排。

## 高频追问 14：Agent 的工具是怎么设计的？

**结论：** 工具应单一职责、参数明确、结果有界、默认只读，并把数据库/日志系统的复杂性隔离在工具后面。

**本项目做法：** 工具包括事故摘要、日志检索、时间线、按 ID 取证、模板统计和 Runbook 查询；`ToolRegistry` 统一注册与调用，检索工具限制条数，Agent 不能直接执行 Shell 或生产修复。

**取舍与限制：** 当前工具是内存实现，真实环境要接 Elasticsearch/OpenSearch、ClickHouse、Loki 或日志平台，并增加租户隔离、超时、重试、速率限制和审计。

## 高频追问 15：Agent 状态和“记忆”是什么？

**结论：** 本项目使用单次任务内的短期状态，不需要长期记忆；状态保存任务、步骤和工具观察，供策略决定下一步。

**本项目做法：** `AgentState` 包含 `task`、`observations` 和 `step`。工具返回值进入 observations，策略通过已有观察判断是否还需调用摘要、检索或时间线工具。

**取舍与限制：** 没有跨 Incident 的长期记忆，也没有把历史结论自动当事实。生产中可把已确认事故沉淀到案例库，但要设置版本、TTL、权限与人工确认，防止旧结论污染新事故。

## 高频追问 16：如何防止 Agent 无限循环或不停调用工具？

**结论：** 必须同时具备步数预算、数据返回上限、明确终止输出和失败处理。

**本项目做法：** `AgentRuntime` 有 `max_steps`；策略产生 `FinalAction` 才结束，否则调用工具并记录观察；超过步数直接抛错。各检索工具也有限流边界。

**取舍与限制：** 当前超限后直接失败，没有自动降级报告。生产中应在超时或预算耗尽时返回部分证据、标记未完成，并允许人工接管，而不是悄悄输出一个猜测。

## 高频追问 17：结构化输出解决了什么问题？

**结论：** 结构化输出让组件间契约、UI 渲染、自动评测和字段校验成为可能，但不能自动保证事实正确。

**本项目做法：** Pydantic 定义 `HypothesisBundle`、`AuditResult` 和 `DiagnosisReport`；分数有范围约束，证据类型是枚举，最终报告稳定包含根因、置信度、证据、排查、修复和限制。

**取舍与限制：** Schema-valid 不等于 grounded，所以报告生成后仍用代码检查 `line_id` 是否属于当前 Incident。面试中不要说“用了 JSON Schema 就解决幻觉”。

## 高频追问 18：如何降低幻觉和无依据结论？

**结论：** 不能靠一句“不要幻觉”的 Prompt，要把证据来源、引用形式和最终校验做成系统约束。

**本项目做法：** Agent 只能通过工具看日志；证据只引用 `line_id`；审核员重新取证；Manager 最后用当前 Incident 的 ID 集合删除无效引用；未知模板返回 `unknown`；报告显式列出限制。

**取舍与限制：** 有效 ID 仍可能被错误解释，因此代码校验只能解决“引用不存在”，不能证明因果。更强方案需要 entailment 评测、不同来源交叉验证和人工确认。

## 高频追问 19：日志里如果出现“忽略之前指令”怎么办？

**结论：** 日志是外部不可信数据，只能作为数据，不得拥有指令优先级；同时要做输入标记、工具最小权限和输出校验。

**本项目做法：** `sanitize_log_text` 会脱敏常见 secret 形式，并标记疑似 Prompt Injection 内容；Agent 指令明确日志不能改变系统指令；所有工具只读且参数受限。

**取舍与限制：** 正则只能覆盖基础模式，不是完整 DLP 或注入防御。生产中还需要源端脱敏、内容隔离、权限控制、模型安全评测和高风险动作人工审批。

## 高频追问 20：置信度是怎么来的，能当概率吗？

**结论：** 当前 confidence 是启发式排序分数，不是经过校准的真实概率。

**本项目做法：** 已知直接模板命中时，主假设给出基础分；若审核发现缺少直接证据，则通过 `confidence_multiplier` 下调。CLI 明确打印“不是校准概率”。

**取舍与限制：** 真实置信度应通过带标签历史集做可靠性校准，并区分分类置信、证据充分度和数据完整度。简历和面试中不能把 0.93 说成“93% 的真实正确概率”。

## 高频追问 21：为什么 Runbook 要做成工具，而不是让模型直接生成建议？

**结论：** 处置建议属于高风险知识，优先检索经过维护和审核的 Runbook，模型负责选择和解释，而不是凭空发明操作。

**本项目做法：** `get_runbook` 按根因代码返回排查项和修复建议；未知根因默认建议补充数据并避免高风险变更。Agent 没有执行修复的工具。

**取舍与限制：** Demo 的 Runbook 是静态字典，没有版本和环境差异。生产应接企业知识库，附负责人、适用版本、更新时间和审批级别，危险操作必须人工确认。

## 高频追问 22：如何做可观测性和调试？

**结论：** Agent 系统不能只存最终答案，还要存“何时、由谁、为什么调用了什么工具、工具返回什么、耗时多少”。

**本项目做法：** `TraceRecorder` 为每次运行分配 `run_id`，记录 `agent_start/tool_call/tool_result/agent_final` 以及 Manager 的门控和 grounding 事件，保存为 JSONL。

**取舍与限制：** 当前 Trace 是本地文件，没有分布式追踪、Token/成本字段和数据保留策略。生产中要接观测平台，并对 Trace 自身做脱敏和访问控制。

## 高频追问 23：如何评测一个日志 RCA Agent？

**结论：** 不能只评最终根因，还要分层评异常门控、根因、证据、工具轨迹、成本、延迟和安全性。

**本项目做法：** `evaluation.py` 计算异常 precision/recall/F1、root-cause accuracy、evidence precision/recall、平均工具调用和延迟，并保留每个 case 的预测与真值。

**取舍与限制：** 当前集太小，且生成规则与识别目录同源，只适合功能回归。生产评测还应包含未知故障、格式漂移、噪声、缺失日志、并发事故、注入样本和专家盲评。

## 高频追问 24：为什么合成评测能达到 1.0？这个结果可信么？

**结论：** 它说明代码按设计运行，不说明模型具备生产泛化能力；高分恰恰要主动解释数据闭环。

**本项目做法：** 6-case smoke 中的 5 个异常场景都被当前 9 类 `CAUSE_SIGNATURES` 覆盖，正常场景没有异常信号，所以这个封闭回归可以完全命中；审核员也使用相同语义签名筛证据。

**取舍与限制：** 这是白盒单元/集成回归，存在场景泄漏和覆盖面有限的问题。最诚实的表述是“6 个确定性场景回归全通过”，而不是“准确率 100%，达到生产水平”。

补充防泄漏措施：事故、title 和 event ID 已改为不透明编号，场景名只留在独立 Ground Truth；但故障模板目录与生成场景仍同源，所以它依然不是未知分布盲测。

## 高频追问 25：Loghub 数据在项目里到底起什么作用？

**结论：** Loghub 用于验证公开数据的读取、字段归一、模板表示、压缩和行级异常基线；它没有直接提供本项目所需的完整微服务 RCA 真值。

**本项目做法：** Adapter 读取 Loghub 的结构化 CSV；BGL 可以用 `Label` 做行级异常基线；模板 ID 用于统计与紧凑表示。根因链实验则使用透明合成 Spring 场景。

**取舍与限制：** 不能把 Loghub 的某条异常标签说成“根因标签”，也不能说 Loghub 是真实公司生产数据。公开数据与合成数据承担的是两类不同验证任务。

## 高频追问 26：BGL 的 `Label` 能不能直接拿来评 RCA？

**结论：** 不能。BGL `Label` 表示单行正常/异常，它既不标注微服务故障根因，也不提供完整的业务传播链。

**本项目做法：** `evaluate_bgl_level_baseline` 只把 `Label != "-"` 当作行级异常真值，用日志 Level 做简单基线，并明确输出 `unit=log_line` 和 scope note。

**取舍与限制：** 行级异常检测成绩不能等同于事故级检测，更不能等同于 RCA 准确率。若要评 RCA，需要事故边界、根因类型、证据行和影响服务等独立标注。

## 高频追问 27：为什么还要自己造 Spring 合成日志？

**结论：** 因为公开数据缺少符合目标场景的完整可控因果链；合成数据适合构造最小闭环和回归测试，但必须透明披露。

**本项目做法：** `synthetic.py` 构造连接池耗尽、线程池饱和、Redis 不可用、支付鉴权失败、磁盘满及正常场景，并把 Ground Truth 与 Agent 可见事件分离。

**取舍与限制：** 合成日志语言整齐、噪声低、模板已知，难度远低于生产。下一步应注入乱序、缺失、重复、跨事故噪声和未知模板，再引入人工标注的脱敏真实样本。

## 高频追问 28：如何避免 Ground Truth 泄漏给 Agent？

**结论：** 评测标签和运行输入必须物理或接口上分离，Agent 只能看到 Incident，Evaluator 才能看到 GroundTruth。

**本项目做法：** P0 物理导出 `incidents.agent.jsonl` 与 `truth.sidecar.json`；`IncidentManager.diagnose` 只收到前者中的 `Incident`，全部诊断结束后 `p0_runner.py` 才关联真值。ID 不透明、所有故障族共享中性服务名、时间戳哈希化，同一 root-evidence 文案/template ID 不跨 split；测试还用 spy manager 检查入参不存在真值字段。

**取舍与限制：** 语料措辞与 `diagnostic_signatures.py` 仍在同仓、同一开发过程演进，所以这是运行时标签隔离，不是独立外部盲测。更严格的泛化测试仍需由另一团队或真实专家构建冻结 holdout。

## 高频追问 29：单 Agent 和多 Agent 的实验说明了什么？

**结论：** 在当前封闭场景中，审核角色能剔除级联症状、提高证据精确率，但会增加调用成本；它不证明多 Agent 普遍优于单 Agent。

**本项目做法：** 在当前 40-case P0 test 中，Single 的 Evidence micro Precision/Recall 为 0.4103/1.0，Multi 为 0.9275/1.0；平均工具调用从 3.6 增至 5.4。两者的 RCA Top-1 都是 0.8125，所以 Auditor 改善的是证据精度，没有改善候选生成器的根因准确率。

**取舍与限制：** 当前是本地确定性策略，毫秒级延迟不能外推真实 LLM；真正选型要同时看 Evidence、RCA、OOD 拒答、Token、p95、结构化失败和维护复杂度。

## 高频追问 30：为什么没上向量数据库和通用 RAG？

**结论：** 这个 Demo 的核心检索键是时间、服务、等级、trace_id、template_id 和 line_id，结构化过滤比语义向量更直接；Runbook 数量也暂时不需要向量库。

**本项目做法：** 日志通过确定性工具检索，Runbook 通过根因代码查表。这样可验证、低成本，也避免相似文本把不同根因混在一起。

**取舍与限制：** 当 Runbook、历史事故复盘和非结构化文档增多时，可以增加混合检索：元数据过滤 + BM25 + embedding + reranker，并单独评测召回和引用正确性。

## 高频追问 31：为什么没有继续使用知识图谱？

**结论：** 知识图谱适合表达稳定拓扑和依赖关系，但无法自动解决日志噪声、事故聚合、证据不足与推理可靠性；当前先用更轻的事件模型和显式故障目录跑通闭环。

**本项目做法：** 服务、trace、模板、时间线等关系目前保存在结构化字段和规则中，Agent 通过工具读取；没有声称实现图数据库或图推理。

**取舍与限制：** 生产阶段可以把 CMDB、服务调用图、部署变更与故障实体接入图查询工具，用于限制候选传播路径；但图谱仍需数据治理，不能把“有图”当成 RCA 效果保证。

## 高频追问 32：可选真实 LLM 路径是怎么接入的？

**结论：** 用适配器替换决策策略，而保持 Incident、工具、输出 Schema、门控和代码级 grounding 不变，这样领域管道不会绑定某个 SDK。

**本项目做法：** `openai_adapter.py` 延迟导入 OpenAI Agents SDK，创建 Hypothesis Agent 与 Evidence Auditor；Python Manager 负责固定调用顺序、结构化中间结果、证据集合相交和最终报告组装；模型名必须显式传入。

**取舍与限制：** 该路径需要额外安装、API Key、网络和单独的兼容性/成本评测。若本人没有真实运行，就只能说“实现了可选适配代码”，不能说“已完成大模型效果验证或线上部署”。

## 高频追问 33：为什么默认不用真实模型？

**结论：** 先用离线策略验证架构闭环和评测方法，可以把模型能力与系统工程问题分开，也降低学习与运行成本。

**本项目做法：** 默认 CLI、测试、Benchmark 都不需要模型；`Policy` 边界允许以后接 LLM。这样没有 Key 时仍能演示 Agent 循环、工具、审计与 Trace。

**取舍与限制：** 离线结果不能代表 LLM 的语言理解和泛化效果。接模型后必须重新跑评测，因为工具选择、格式遵循、幻觉、成本和延迟都会改变。

## 高频追问 34：如果接入真实模型，Prompt 怎么设计？

**结论：** Prompt 负责角色边界和决策原则，数据访问、权限和事实校验要由代码保证；Prompt 不应承载全部业务知识。

**本项目做法：** 三段指令分别限定根因专家、证据审核员和 Manager；强调日志是不可信数据、只能引用工具返回 ID、证据不足保留不确定性、不得执行修复。

**取舍与限制：** 当前没有系统化 Prompt 版本管理和对抗评测。生产中要固定版本、记录模型参数、维护回归集，并测试指令冲突、注入、长上下文和工具错误。

## 高频追问 35：遇到未知故障或工具失败怎么办？

**结论：** 正确策略是降级为“不足以判断”，保留已有证据和下一步采集建议，而不是强制从已知类别中选一个。

**本项目做法：** 未命中模板时返回 `unknown`，使用保守 Runbook，并在 limitations 标明规则库未覆盖；运行时把工具异常作为观察返回给策略，避免一次异常直接伪装成成功。

**取舍与限制：** 离线策略目前对连续工具失败的恢复有限，步数耗尽会抛错。生产中应增加重试策略、熔断、备用数据源、partial report 和人工升级通道。

## 高频追问 36：这个系统会自动修改生产配置吗？

**结论：** 不会。当前系统只读日志并给出排查与处置建议，最终动作由人确认；RCA 和 remediation execution 必须分权。

**本项目做法：** 工具集中没有 Shell、Kubernetes 写操作、数据库变更或告警关闭；Runbook 输出只是建议；日志注入也不能获得执行能力。

**取舍与限制：** 自动化修复可以作为后续独立阶段，但需要白名单、审批、dry-run、幂等性、回滚和 blast-radius 控制。绝不能把当前 Demo 描述成“自动修复生产故障”。

## 高频追问 37：安全和隐私方面做了什么？

**结论：** 安全从数据进入系统前开始，包括脱敏、最小权限、租户隔离、不可信内容处理和全链路审计。

**本项目做法：** 当前实现对常见 password/API key/token 形态做基础脱敏，对指令型文本打标；Agent 只使用只读有界工具；Trace 可审计调用过程。

**取舍与限制：** 正则脱敏只是演示基线，没有覆盖个人信息、业务字段、编码绕过和多租户授权。真实部署必须接入企业 DLP、RBAC、密钥管理、审计和数据保留制度。

## 高频追问 38：如何把它接入 Spring/Java 生产系统？

**结论：** Java 服务继续按统一规范输出日志和 Trace；Agent 服务独立消费日志索引或事件流，通过只读 API 查询，不应嵌进业务请求链路。

**本项目做法：** 当前 `LogEvent` 就是语言无关边界；`spring_parser.py` 已展示指定 Logback layout 和多行堆栈怎样映射为该契约，报告可进一步通过 REST/消息队列提供给告警平台或工单系统。

**取舍与限制：** Demo 没有实现 Java SDK、Kafka、ES、鉴权和部署。面试中可以讲集成设计，但要用“生产方案会……”而不是“项目已经接入……”。

## 高频追问 39：上线前你还会补哪些测试？

**结论：** 除单元测试外，必须补数据漂移、未知故障、检索召回、安全攻击、模型版本回归和人工可用性评测。

**本项目做法：** 现有测试覆盖合成场景、门控、Agent 输出、工具边界、Loghub 读取、Spring 多行解析、压缩和 BGL 行级基线；Benchmark 保存逐 case 结果。

**取舍与限制：** 缺少大规模并发、长时间稳定性、真实 SDK、Token 成本和脱敏生产集测试。面试时主动列出这些缺口，通常比声称“已非常完善”更可信。

## 高频追问 40：如果给你真实生产数据，下一步怎么迭代？

**结论：** 先建立可回放、可标注、可分层评测的数据闭环，再换更复杂模型；不要先堆 Agent 数量。

**本项目做法：** 计划顺序是：脱敏采样 → 专家定义 Incident 与证据 → 建 train/dev/test 时间切分 → 测门控与检索召回 → 接真实 LLM → 做单/多 Agent 消融 → 灰度只读建议 → 人工反馈回流。

**取舍与限制：** 真实标签昂贵且会随系统变化，需记录“不确定”和多根因；线上反馈也可能有选择偏差。模型升级必须以固定回放集和安全门槛为准。

## 30 秒项目介绍模板

> 我实现了一个离线优先的智能日志 RCA Agent。系统将 Spring/Logback 与 Loghub 结构化日志统一成事件，按 trace ID 或时间窗口聚合；异常门控后，由 Manager 调用根因假设与证据审核 Agent，通过只读工具和 line_id grounding 输出根因、证据链与排查建议。项目没有引入 RAG 或知识图谱；本地 P0 使用 120 个标签侧车案例和 16 个 Loghub 数据集的真实消息噪声，覆盖已知故障、正常、OOD、证据删除和 trace 污染，并保留失败样本。真实 LLM 是可选适配路径，没有 API Key 的结果不会冒充实测。

## 2 分钟项目介绍模板

> 我做这个项目时先把问题拆成“数据面”和“推理面”。数据面不依赖 LLM：负责日志格式统一、模板表示、Incident 聚合、异常门控和有界检索。推理面采用 Manager 编排：Hypothesis Agent 找根因候选和证据，multi 模式再调用 Evidence Auditor 独立核验，最后由 Manager 输出固定 Schema。这样做的关键原因是，生产日志里最常见的错误行经常只是传播症状，必须把最早的直接故障、支持证据和下游影响分开。
>
> 为了控制成本，我没有把几万行日志直接塞进上下文，而是先取摘要与 ERROR/WARN，再按 line_id 回取时间线；正常事件在门控阶段直接结束。为了降低幻觉，证据只能引用工具返回的 line_id，审核后还有代码级 grounding。每次工具调用都会进入 JSONL Trace，便于调试和评测。
>
> 项目默认用离线规则策略，是为了在没有公司数据和 API Key 的条件下把架构、工具、评测跑通，并不把规则包装成 LLM。6 个透明场景只承担 smoke regression；主要 P0 是 120 个标签隔离的开发者合成案例，其中 test 40 个。当前 test 的检测 F1 为 1.0，无条件 RCA Top-1 为 0.8125；direct 证据可见的 26 个案例 Top-1 为 1.0，删除 direct 的 6 个案例和 4 个 OOD 案例全部安全弃权。Multi 的证据 micro precision 为 0.9275，Single 为 0.4103，但多 Agent 平均工具调用从 3.6 增至 5.4。这个结果能证明实现与安全机制可复现，不能证明生产泛化。后续有真实脱敏数据时，会先补事故级标注和时间切分 holdout，再对真实 LLM 的质量、Token、延迟和安全做评测。

## 绝对不能夸大的边界

以下说法在当前项目证据下不成立：

- “已在公司生产环境上线”——当前是本地 Demo，没有真实企业部署证据。
- “使用了公司真实生产日志”——当前使用公开 Loghub 与透明合成日志。
- “支持每天百万/亿级日志”——没有吞吐、并发、存储和压力测试。
- “RCA 准确率 100%”——P0 test 的无条件 Top-1 是 0.8125；只有 direct 证据可见子集是 1.0，而且仍是开发者合成分布。6 个封闭场景的 1.0 只属于 smoke regression。
- “Loghub 提供了完整根因标签”——BGL `Label` 是行级异常标签，不是微服务根因标签。
- “核心是大模型自动推理”——默认路径是离线确定性规则；真实 SDK 是可选适配路径。
- “多 Agent 一定优于单 Agent”——当前只观察到特定合成集上的证据 precision 改善，并付出更多调用。
- “实现了自动修复”——当前仅给建议，所有工具只读。
- “实现了知识图谱”——当前没有图数据库和图推理实现。
- “置信度 0.93 表示 93% 正确率”——当前分数未经概率校准。
- “JSON 化后 Token 大幅降低”——完整 JSON 可能更大；节省来自模板化和检索裁剪。
- “彻底解决 Prompt Injection 与敏感信息泄漏”——当前只有基础正则和权限边界。
- “已验证真实 LLM 的成本、延迟和效果”——除非你本人实际运行 SDK 路径并保存可复现实验。
- “排查建议可以直接在生产执行”——Runbook 是演示知识，必须结合环境并由人审核。

## 面试回答的最后原则

遇到没做过的内容，用三句话回答最稳：

1. **当前实现到了哪里：** 指向具体代码和可复现实验。
2. **为什么停在这里：** 数据、成本、权限或 Demo 目标是什么。
3. **生产上怎么补：** 说清接口、评测和风险控制，而不是假装已经完成。

一个可信的 Demo 不需要伪装成生产系统。真正能打动面试官的是：你知道 Agent 适合做什么、不适合做什么，能用证据解释设计选择，也知道下一步如何把它安全地推向真实环境。
